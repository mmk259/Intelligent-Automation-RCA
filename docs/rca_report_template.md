
# Root Cause Analysis (RCA) Report Template

This document defines a proposed structure for presenting RCA results generated by Intelligent Automation RCA. Not every field is currently populated by the implemented system.

## 1. Incident Summary

| Field | Description |
|---|---|
| Incident ID | Unique incident identifier, where available |
| Timestamp | Incident timestamp, where available |
| Automation Platform | Platform associated with the incident |
| Process Name | Name of the automation process |
| Workflow Name | Name of the affected workflow |
| Failed Activity | Activity associated with the failure |
| Exception Type | Identified exception type |
| Exception Message | Extracted exception message |
| Incident Category | Assigned incident category |
| Incident Subcategory | Assigned incident subcategory |

## 2. Incident Description

A concise description of the incident based on the supplied execution log and available context.

## 3. Observed Evidence

Information directly extracted from the execution log or incident context.

Evidence should be distinguished from assumptions and model-generated explanations.

## 4. Retrieved Knowledge

Relevant knowledge-base entries retrieved during diagnosis, including:

- Root-cause candidates
- Recovery recommendations
- Related incident patterns
- Similarity scores, where applicable

Retrieval similarity indicates relevance according to the retrieval method. It does not confirm that a retrieved entry represents the actual cause.

## 5. Probable Root Causes

List possible root causes in order of relevance.

For each candidate, include:

- Proposed root cause
- Supporting evidence
- Related knowledge-base entry
- Verification method
- Remaining uncertainty

A probable root cause should not be presented as confirmed without sufficient supporting evidence.

## 6. Diagnosis Rationale

Explain how the available evidence and retrieved knowledge support each proposed explanation.

Distinguish between:

- Directly observed evidence
- Retrieved knowledge
- Model-generated inference
- Unverified hypotheses

## 7. Recommended Recovery Actions

List recovery actions relevant to the incident.

Indicate where human review or environment-specific verification is required before execution.

## 8. Prevention Recommendations

Provide preventive recommendations where supported by the available information. Clearly identify general suggestions that have not been validated against the incident.

## 9. Verification Results

Where applicable, include:

- Verification outcome
- Unsupported or insufficiently grounded claims identified
- Revision feedback
- Whether a revised report was generated
- Remaining uncertainty

A verifier PASS result represents the assessment of the implemented verification component, not a guarantee of diagnostic correctness.

## 10. Score Interpretation

Scores used by the system must be identified according to their actual meaning:

- **Classifier match score:** Indicates the strength of a rule-based classification match.
- **Retrieval similarity score:** Indicates similarity between a query and retrieved knowledge.
- **Knowledge-base confidence label:** Represents the qualitative confidence assigned to a knowledge-base entry.
- **LLM-generated confidence or uncertainty:** Represents the language model's own assessment.

These values are not calibrated probabilities and should not be combined into a single probability of diagnostic correctness.

## 11. References

List the relevant knowledge-base entries, historical incidents, and external references used in the diagnosis.
